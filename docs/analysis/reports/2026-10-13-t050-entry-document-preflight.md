## Highest-impact finding: current three-task scheduling order

The earlier hypothesized B → A → B → EL0 → A ordering is false. Source and retained earlier evidence agree on:

1. B prints waiting; blocks on receive.
2. A prints sending; delivers to B and yields.
3. EL0 hello runs, greets in debug only, then exits.
4. B resumes, receives and queues reply; explicitly yields.
5. A receives reply, prints completion/timing and spins permanently.

Source chain: `bsp-qemu-virt/src/main.rs:1600–1643` registers B, A, user; idle is a separate fallback. `kernel/src/sched/mod.rs:104–136` implements FIFO enqueue-back/dequeue-front. B blocking selects A at `:1453–1484`. A's delivery calls `unblock_receiver_on` (`:628–645`, `:1302–1308`), appending B behind the already-ready user. `yield_now` appends A and dequeues user (`:1115–1150`). User exit calls the free `task_exit_current` and dispatches B (`:979–994`). B reply's explicit yield selects A (`main.rs:621–659`). A reply/completion are contiguous (`main.rs:735–767`). Queue evolution: initial [B,A,U] → B runs, [A,U] → B blocks, A runs, [U] → delivery appends B, [U,B] → yield appends A, U runs, [B,A] → U exits, B runs, [A] → B yields, A runs, [B]. Idle never runs in this path; B's post-yield spin tail never resumes.

Retained comparison evidence fully read: `docs/analysis/reports/2026-10-13-t045-architecture-evidence/debug.qemu.log` (30 lines), `release.qemu.log` (29), and `metadata.json`. These are clean source `4ad0b3d8a9d43310fcd937013131bffadcc803d7`, not T-050 evidence. Debug log lines 8–9 show B/A; 17 greeting; 25 exit; 26 B reply; 27 A reply; 28 completion. ### Timer clarification within approved factual-document scope

The actual source has two distinct algorithms: hal/src/timer.rs:145–160 computes nearest-integer resolution_ns_for_freq (clamped to at least 1 ns), whereas ns_to_ticks at 207–220 uses saturating ceiling division for absolute deadline conversion. The latter's existing rationale at 178–186 expressly cites ADR-0010's reaches-or-exceeds contract. BSP timer implementation calls this helper; glossary prose can describe that existing behavior without choosing a new policy. The QEMU 62.5 MHz case gives exactly 16 ns resolution, but does not establish a rounding rule for arbitrary frequencies.

There is an existing wording discrepancy: Timer::resolution_ns rustdoc at hal/src/timer.rs:52–53 and ADR-0010:78 describe deadlines as rounded to the nearest resolution multiple. ADR-0010:76 instead specifies reaching or exceeding the requested deadline, and its 2026-04-28 revision note at line 145 records the implemented IRQ half. The explicit implementation-review history in docs/analysis/tasks/phase-b/T-012-exception-and-irq-infrastructure.md:112 identifies d820a88's floor-to-ceiling correction to honor reaches-or-exceeds, plus 5c9cf06's regression case frequency 3 Hz / 333333334 ns → 2 ticks. Those are existing decision/implementation authorities; T-050 needs only accurate source-qualified wording, with no runtime change, new normative rounding policy or extra ADR/rider. Keep this discrepancy visible to root for its separate T-055 authority/index assessment; do not silently rewrite an accepted ADR body during T-050.
