### New finding SEC-T034-R1-01 — HIGH: tee discards production smoke failure

**Location:** `.github/workflows/ci.yml:237` and `:243`, the debug and release production smoke `run:` pipelines; no workflow/job/step shell override exists at this tip.

**Problem and impact:** each command runs `tools/smoke.sh ... 2>&1 | tee ...` under GitHub's unspecified Linux shell, `/usr/bin/bash -e {0}`. This shell does not enable `pipefail`. When smoke correctly rejects missing EL0 markers, a fault, or a forbidden release greeting with status 1, successful `tee` makes the step return 0. Therefore the production guest rejection is not a blocking CI result. An actual guest regression or execution failure can be hidden by the logging wrapper if later independent checks pass. This directly defeats the requested merge-gating runtime assurance; there is no claim that the observed clean hosted boot itself was bad.

**Proof:** official [GitHub workflow shell documentation](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) distinguishes unspecified `bash -e` from explicit `shell: bash`, which adds `-o pipefail`. Supplied hosted log `/tmp/tyrne-b21-step6/hosted-qemu.log:748` and `:823` confirms both exact production steps actually used `/usr/bin/bash -e {0}`.

Independently copied the unchanged smoke script into a disposable path containing spaces/metacharacters, extracted each exact `run:` command from the workflow, supplied an explicit private ELF, and used a QEMU stub only to deliver controlled traces. These are workflow-integration fixtures, not claims of actual fault injection:

| Trace delivered to actual smoke | Actual default shell exit | Explicit Bash with pipefail exit | Actual diagnostic |
|---|---:|---:|---|
| Debug completion only | 0 | 1 | Greeting and userspace-exit markers missing |
| All debug markers plus `Data Abort` | 0 | 1 | Panic / CPU-fault class appeared |
| Release exit/completion plus greeting | 0 | 1 | Forbidden userspace greeting |

Complete six-case output is `/tmp/tyrne-b21-t034-r1-security-pipeline.json`. The smoke script's own `set -euo pipefail` affects its child shell, not the parent workflow pipeline. The direct Python harness correctly checks smoke return codes but does not exercise this outer `tee` pipeline, explaining why all 23 cases can pass while the integration defect remains.

**Required correction:** enable Bash pipefail for both production steps, for example job-scoped `defaults.run.shell: bash`, and add a regression that sends a known rejecting trace through the same CI pipeline/shell and asserts nonzero plus the intended smoke diagnostic. Re-run relevant local checks and hosted clean guests, and review the fix before required-check registration. A fix is not present in this reviewed range.
