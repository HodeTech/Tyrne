## 1. Capability correctness

Adversarial frame: *does the migration weaken any capability check, open an ambient-authority path, or change who may perform a privileged operation?*

- **T-022 introduces no syscall, no capability type, no rights bit, and no capability check.** OK — the diff touches `linker.ld`, `mmu_bootstrap.rs`, `main.rs` (`kernel_entry`/`kernel_main_high`), `mmu.rs` (`activate`), `hal/mmu/mod.rs` (the `phys_to_kernel_va`/`kernel_va_to_phys` helpers + offset), and docs. None of the capability surface (`cap/`, `ipc/`, `syscall/dispatch.rs`) is modified. The capability model is byte-for-byte unchanged.
- **The migration is an *isolation strengthening*, not a relaxation.** OK — freeing `TTBR0_EL1` (`MSR TTBR0_EL1, xzr` + `EPD0 = 1`) makes the kernel **structurally absent** from the low half. Before T-022 a future EL0 task would have required the kernel to be present-but-`AP`-protected in every per-task `TTBR0` (a standing per-descriptor invariant). After T-022 the kernel lives only in `TTBR1` (`AP = 0b00`, EL0-no-access) and is simply not mapped in the user regime — the high-assurance end-state ([ADR-0033 §Decision drivers 1](../../../decisions/0033-kernel-high-half-migration.md)). No capability is granted, widened, or bypassed.
- **The per-task `TTBR0` swap mechanism (`QemuVirtMmu::activate`) does not over-grant.** OK — `activate` ([`bsp-qemu-virt/src/mmu.rs:191-243`](../../../../bsp-qemu-virt/src/mmu.rs)) writes the address-space root PA into the freed `TTBR0_EL1`, clears `EPD0`, and `TLBI VMALLE1`s. It is reached only through [`activate_address_space_handle`](../../../../kernel/src/mm/address_space.rs) which resolves a live `AddressSpaceHandle` first (fail-soft on a stale handle). The AS itself is minted through the cap-gated `cap_create_address_space` (B3, unchanged). In v1 the swap fires only once, for the bootstrap AS; the *distinct*-AS swap is B6. No ambient authority over another AS is created.

## 2. Trust boundaries

Adversarial frame: *during the regime switch, is there any window where an untrusted input crosses, or where the about-to-be-isolated kernel becomes reachable/leakable?*

- **No userspace exists during the migration — it runs entirely in the boot window with `DAIF` masked.** OK — the migration executes inside `kernel_entry`/`kernel_main_high`, before any task is created, before the GIC unmask, with `DAIF` masked from `_start` ([`boot.s`](../../../../bsp-qemu-virt/src/boot.s) `msr daifset, #0xf`). No EL0 code, no IPC, no syscall, no interrupt can be taken during the switch. There is no trust boundary *crossed* by the migration itself; it *builds* the boundary that B6 will cross.
- **The `+0x400` lower-EL syscall path is installed but unreachable in v1 — `EPD0 = 1` is the hard gate.** Flagged (forward; non-blocking; the central forward statement). The migration ends with `TCR_EL1.EPD0 = 1`, so **any** `TTBR0` walk faults until a per-task AS activates. Combined with there being no EL0 task in v1, the `+0x400` vector (and `syscall_entry`) is structurally unreachable by untrusted code. This is what makes the **T-021 carry-forward gate #1** (the syscall user window is currently the *whole* high-half RAM extent — `SYSCALL_USER_WINDOW_LEN = PMM_EXTENT_END − START`, base `phys_to_kernel_va(PMM_EXTENT_START)`, [`bsp-qemu-virt/src/syscall.rs:88-110,173-176`](../../../../bsp-qemu-virt/src/syscall.rs)) **harmless today** yet **mandatory to close before B6 opens a real EL0 task**: a debug-console-cap-holding EL0 task could otherwise pass an in-window *kernel* high VA and have EL1 copy privileged memory to the console. Tracked at [phase-b.md §B6 gate #1](../../../roadmap/phases/phase-b.md#milestone-b6--first-userspace-hello); see Verdict.
- **The panic-handler regime fallback (review-round-3) does not introduce an unmapped-alias dereference.** OK — `panic` ([`bsp-qemu-virt/src/main.rs:1595-1620`](../../../../bsp-qemu-virt/src/main.rs)) reads `SP` and selects the UART MMIO alias by regime: `sp >= KERNEL_HIGH_HALF_OFFSET → phys_to_kernel_va(PL011_UART_BASE)` (high alias, valid once the trampoline rebased `SP` and `TTBR1` is live), else `PL011_UART_BASE` (low identity, valid pre-migration). The boundary is exact: the boot/kernel stack lives in the RAM region (`0x4000_0000+`), so a low `SP` is `< OFFSET` and a high `SP` (`OFFSET + 0x4…`) is `> OFFSET`; `OFFSET` itself is never a valid `SP`. A panic in *either* regime prints through a mapped alias instead of translation-faulting — a debuggability hardening, not a new boundary.

## 3. Memory safety

Adversarial frame: *can any step of the regime switch violate a memory-safety invariant — a stale translation, a wild `SP`, a mis-mapped `br` target, or a wrap in the new PA↔VA helpers?*

- **UNSAFE-2026-0031 (trampoline + `TTBR0`-free) is policy-conformant and its invariants hold.** OK — re-traced against [`main.rs:976-987`](../../../../bsp-qemu-virt/src/main.rs) (trampoline) and `:1028-1043` (`TTBR0`-free): (a) **both regimes live across the `br`** — `high_half_activate` published `TTBR1` + cleared `EPD1` with `DSB ISH`-before-`MSR`, and `TTBR0` is nulled only *after* the crossing; (b) **`VBAR`-high + `ISB` before the `br`** — a synchronous fault on the first high fetch vectors to a `TTBR1`-mapped handler, not a stale low vector; (c) **`br` target in the `PXN = 0` image window** — `high_entry = OFFSET | (kernel_main_high & 0xFFFF_FFFF)`, guarded by `high_half_alias`'s `debug_assert!` (`main.rs:838-844`); (d) **`SP` rebase sound under `options(noreturn)`** — no epilogue to mismatch the changed `SP`; (e) **`DAIF` masked throughout**; (f) **no live low-VA pointer survives** (`StaticCell`s written only in `kernel_main_high`, post-crossing). The `TTBR0`-free is register-only (`options(nostack, nomem)`), so no `DSB`-before-`TLBI` is required. The entry carries the second-reviewer requirement and is smoke-verified (axis 4).
- **The high-half table writes + sysreg writes are covered by the 0022/0023/0024 Amendments and re-verified.** OK — `high_half_activate` ([`mmu_bootstrap.rs:308-366`](../../../../bsp-qemu-virt/src/mmu_bootstrap.rs)) writes three table descriptors into the two new, pre-zeroed, `.bss`-resident, single-core-owned high-half root frames (`__boot_pt_l0_hh[511]` → `l1_hh`; `l1_hh[508]`/`[509]` → the **shared** `L2_low`/`L2_high`), indices masked `< 512`; then `DSB ISH` → `MSR TTBR1_EL1` → `ISB` → `MSR TCR_EL1` (EPD1-cleared constant, every `TTBR0` field byte-stable, host-tested) → `ISB`. No aliasing (the L2 tables are intentionally shared — a block descriptor's output PA is identical via either VA); no uninitialised read (unwritten slots are zero = invalid descriptors).
- **The hardened range helpers (review-round-3) fail fast and cannot fire in v1 — including on the panic path.** OK — `phys_to_kernel_va`/`kernel_va_to_phys` ([`hal/src/mmu/mod.rs:94-132`](../../../../hal/src/mmu/mod.rs)) now use `assert!` (not `debug_assert!`) so an out-of-window PA/VA fail-stops in release rather than wrapping to a wild pointer (CLAUDE.md #1 conservative). Adversarial probe — *can the assert fire during boot, or double-panic in the panic handler?* No: every v1 call site passes an in-window value (QEMU `virt` PA range `< 0x4800_0000 ≪ 4 GiB`; every VA fed to `kernel_va_to_phys` is a high-half direct-map VA whose recovered PA is `< 4 GiB`). The panic handler's only call is `phys_to_kernel_va(PL011_UART_BASE)` with `PL011_UART_BASE = 0x0900_0000` (compile-time constant, in-window) → the assert provably passes → **no double-panic**. On host builds (`OFFSET == 0`) the `OFFSET == 0 || …` short-circuit makes the assert a no-op, so the PMM/loader host tests (which deref real host-backed frames) are unaffected. The `# Panics` doc sections were added so `clippy::missing_panics_doc` (pedantic, `-D warnings`) stays green.
- **No use-after-free, no aliasing violation, no uninitialised exposure.** OK — single-core boot, `DAIF` masked, no concurrent writer; the abandoned `kernel_entry` low frame is discarded by the `br`-away; `kernel_main_high` starts a self-consistent frame on the high stack alias (same physical bytes). `cargo miri test --workspace --exclude tyrne-bsp-qemu-virt` is clean over the host suite (offset 0; the migration asm is aarch64-only and not Miri-reachable, which is the correct boundary — its verification is the QEMU smoke + the §Simulation review).

## 4. Kernel-mode discipline

Adversarial frame: *does the migration allocate, loop unboundedly, hold a long critical section, or add a hot-path panic?*

- **No allocation, no unbounded loop, no new hot-path panic.** OK — the migration is a fixed, straight-line sequence of sysreg writes + barriers + one `br`; `high_half_activate`'s only loops are the bounded table-fill loops inherited from `mmu_bootstrap` (`< ENTRIES_PER_TABLE`). The new `assert!`s are a single predictable branch on a value that cannot occur in v1 (axis 3), not a reachable panic. No heap, no ISR (interrupts masked), no lock.
- **The critical "no-rollback" window is design-time-verified, not runtime-guarded.** OK (by design) — once the `br` executes, `kernel_main_high` destroys the low regime; there is no runtime rollback (ADR-0033 §Simulation row 4). Safety is the per-region table verification + the ordering/`PXN`-window pins + the QEMU smoke fail-stop. This is the accepted, documented discipline for a boot-time regime switch, not a defect.

## 5. Cryptography

Not applicable — T-022 introduces no cryptographic primitive, RNG, or key handling. The migration is page-table + system-register manipulation. Unchanged since the B5 N/A finding.

## 6. Secrets and logging

Adversarial frame: *does the migration add a channel that leaks kernel-internal addresses or state?*

- **No new log path; the new boot marker leaks nothing sensitive.** OK — the migration adds one boot line, `tyrne: high-half active` (`main.rs:1068`), a fixed string carrying no address or secret. The `phys_to_kernel_va`/`kernel_va_to_phys` helpers compute addresses but do not log; their `assert!` messages are fixed strings (no address interpolation). No capability bits, handles, or register contents are emitted by the migration path.
- **`KERNEL_HIGH_HALF_OFFSET` is a compile-time constant, not a secret.** OK — the high-half offset is a fixed, public layout constant (documented in `hal/src/mmu/mod.rs` + boot.md + ADR-0033). KASLR is not a v1 feature; there is no address-randomisation secret for the offset to leak. The panic handler prints the panic message (unchanged behaviour); it does not newly expose register/page-table state.

## 7. Dependencies

- **Zero-extern preserved.** OK — T-022 adds no crate. The migration uses only `core::arch::asm!` + `core::ptr::write_volatile` + the in-tree `tyrne_hal` helpers. `Cargo.lock` is unchanged (four in-tree workspace crates). ADR-0006's zero-extern supply-chain stance holds; `cargo-vet`/`cargo-audit` remain no-ops.

## 8. Threat-model impact

Adversarial frame: *how does the migration reshape the threat model, and is every residual gap reconciled with [`security-model.md`](../../../architecture/security-model.md) and honestly documented?*

- **This is the structural kernel/user isolation foundation — a net reduction of attack surface.** OK — the kernel is now *absent* from the `TTBR0_EL1` regime an EL0 task will run on, rather than present-but-`AP`-protected. This removes the Meltdown/transient-execution substrate (no kernel data resident in a user-active regime) and replaces a standing per-descriptor `AP`/`UXN`/`PXN` invariant (must-never-be-wrong on every AS forever) with a structural absence ([ADR-0033 §Consequences §Positive](../../../decisions/0033-kernel-high-half-migration.md)). The high-half kernel/user split is the conventional high-assurance shape (seL4, Linux KPTI-adjacent).
- **The privileged-side W^X gap is a documented, EL0-unreachable, deferred item — not a live defect.** Flagged (forward; non-blocking). v1 maps the whole high-half RAM window `PXN = 0` (RWX-equivalent — kernel image *and* the physmap/PMM/page-table/copy-user data live in one `PXN = 0`, `AP = 0b00` window), exactly as the identity map it replaced did (T-016). Because `AP = 0b00`, **EL0 has no access** — this is a privileged-side W^X gap only, never an EL0-reachable one. The per-section hardening (image `PXN = 0` RX vs physmap `PXN = 1` data) is the named end-state deferred to **ADR-0034** (kernel-image section permissions), a reserved-but-unwritten slot ([decisions/README.md §0034 footnote](../../../decisions/README.md)). B6 decides harden-now vs defer; per [phase-b.md §B6](../../../roadmap/phases/phase-b.md#milestone-b6--first-userspace-hello) it is hardening, not a functional blocker.
- **Reconciliation against `security-model.md` §Invariants** — each re-confirmed for the migration:
  - "No privileged operation without the authorizing capability" / "No ambient authority" — OK (§1; the migration adds no operation and no authority).
  - "Capabilities unforgeable / per-subject" — OK (§1; untouched).
  - "The kernel never dereferences raw userspace pointers" — OK for v1 (§2; `EPD0 = 1` + no EL0 task), **with gate #1 as the named B6 precondition** before this invariant must hold against a real EL0 task.
  - "`unsafe` is audited" — OK (§3; UNSAFE-2026-0031 + the 0022/0023/0024 Amendments, second-reviewer-flagged).
  - "Bounded kernel state / panic-free on untrusted input" — OK (§4; no untrusted input reaches the migration; the new asserts cannot fire in v1).
- **Forward limit (Pi 4 / > 4 GiB).** OK (documented). The single linear offset `0xFFFF_FFFF_0000_0000` bounds the direct map to the low 4 GiB of PA, and the migration mask assumes the image PA `< 4 GiB`; a future > 4 GiB BSP needs a different offset + revisited mask (boot.md §Forward limit + hal/mod.rs). Not a v1 concern; the new `assert!` (axis 3) is precisely the fail-fast guard for any future site that violates this.

## Verdict

**Approve.** No live security defect found; **no fix required** to proceed.

All eight applicable axes pass (cryptography N/A). T-022 changes the kernel's own translation regime and the kernel/user isolation boundary — among the most security-sensitive changes possible — and does so as a *strengthening*: it makes the kernel **structurally absent** from the user-active `TTBR0_EL1` regime, removing the Meltdown substrate and replacing a standing per-descriptor `AP` invariant with structural absence. The migration adds no capability, syscall, ambient authority, log channel, or dependency. The sole `unsafe` entry (UNSAFE-2026-0031) is policy-conformant with the second-reviewer requirement and is smoke-verified fault-clean (`-d int,unimp`: the new `tyrne: high-half active` marker, run-through to `tyrne: all tasks complete`, exactly the 2 expected `SVC` exceptions, **zero** new Translation/Permission/Abort fault class — ADR-0033 §Simulation row-4 abort gate). The review-round-3 hardenings (the fail-fast `assert!` range guards and the regime-correct panic-handler UART alias) are sound and cannot misfire in v1 (verified incl. the no-double-panic property on the panic path). `cargo fmt`/`host-clippy`/`kernel-clippy`/`kernel-build` clean; 340 host tests; `cargo miri test --workspace --exclude tyrne-bsp-qemu-virt` clean.

The `current.md` "awaiting explicit security review" flag for T-022 / UNSAFE-2026-0031 is **discharged** by this pass.

### Forward-flagged items (carry-forward; non-blocking; pre-B6)

- **T-021 carry-forward gate #1 (the single most important pre-B6 gate)** — before a real EL0 task can reach `syscall_entry`, `console_write`'s user window must become **per-task** (derived from the EL0 task's mapped image+stack region, not the whole RAM extent) and the int-to-pointer deref must become a per-page user-VA → kernel-VA translation walking the task's own `TTBR0`, returning `SyscallError::FaultAddress` (never panic). Tracked at [phase-b.md §B6](../../../roadmap/phases/phase-b.md#milestone-b6--first-userspace-hello).
- **Gates #2 / #3** — per-task `SP_EL1` init for the `+0x400` entry; `SYSCALL_STUB_TABLE` → scheduler current-task table. Both B6 preconditions.
- **ADR-0034 (kernel-image section W^X)** — the privileged-side `PXN = 0`-whole-RAM gap (axis 8). Decide harden-now vs defer at B6; hardening, not a functional blocker.
- **Forward-limit (> 4 GiB PA)** — the single-offset direct map + migration mask assume image PA `< 4 GiB`; a future Pi 4-class BSP revisits both (the new `assert!` is the fail-fast guard).
