## 1. Capability correctness

1. **Privileged operations require authority — OK for the changed descriptions.** Malicious-caller question: can a reader mistake an internal helper for a callable EL0 service and gain authority without a cap? `overview.md` distinguishes the five ABI numbers from internal capability, task, AS and IRQ operations; `kernel/src/syscall/dispatch.rs:129` dispatches exactly that surface. Send/receive use `SEND`/`RECV`, and debug console validates `DebugConsole`/`CONSOLE_WRITE`. Yield/exit act on the bound current task and intentionally have no capability argument. The kind-only memory APIs are expressly identified as trusted kernel APIs, not an untrusted physical-memory authorization boundary.

2. **Narrowest sufficient capability — OK for documented scope.** Malicious-caller question: can a broad or wrong-kind token substitute for the operation's expected authority? `validate_debug_console_cap` (`dispatch.rs:312`) resolves handle, kind and `CONSOLE_WRITE`; `ipc_send`/`ipc_recv` validate endpoint operation rights. The overview's address-space paragraph explicitly says `cap_map`/`cap_unmap` lack per-operation MAP rights and physical-memory ownership checks. `cap_create_address_space` (`address_space.rs:540`) checks `DERIVE`, narrowing, derivation depth and capacity. No claim that all existing internal helpers meet a future narrow-rights design remains.

3. **Checks before observable effects — OK for the asserted paths.** Malicious-caller question: can an unauthorized console request read or print user/kernel bytes, or can failed transfer consume authority? ABI decoding precedes dispatch; debug console checks capability, complete range and all USER mappings before emitting a chunk (`dispatch.rs:243`). The loader validates arguments, parent cap, VA, budget and source overlap before creating mappings (`task_loader.rs:507`). IPC send checks source transfer authority and endpoint availability before `cap_take`; receive checks table capacity before moving endpoint state. No universal timing-side-channel guarantee is inferred.

4. **Move-only transfer — OK.** Malicious-caller question: can the sender keep a usable copy or lose authority on a rejected receive? `Capability` is not Copy/Clone; `ipc_send` moves through `cap_take` into endpoint state, and `ipc_recv` installs it only after receiver capacity preflight (`ipc/mod.rs:320`, `:406`). The corrected two-stage prose matches these bodies. The test `recv_with_full_table_preserves_pending_cap` (`:1350`) verifies rejection followed by successful retry, while the sender-transfer tests verify movement. No claim that receive capacity is checked during send remains.

5. **Explicit duplication authority — OK.** Malicious-caller question: can safe copying manufacture authority? `cap_copy` (`cap/table.rs:194`) checks `DUPLICATE` and rights subset before slot allocation. The overview says copying authority uses the table API and internal management APIs are not additional EL0 syscalls. This describes the existing mechanism without claiming arbitrary kernel code cannot mint roots.

6. **Atomic revocation — N/A to changed behavior.** Malicious-caller question: does the refresh add a revocation race or promise global cross-task revocation? No revocation implementation or syscall is added; the overview merely lists revocation among internal APIs and does not promise cross-table or SMP atomicity. Existing `cap_revoke` (`cap/table.rs:329`) remains table-local, capability-gated and bounded; loader rollback correctly names `cap_drop`, not revocation or object destruction. This outcome does not certify future concurrent or cross-table lifecycle behavior.

## 2. Trust boundaries

7. **Userspace input validation — OK for the described surface.** Malicious-caller question: can crafted numbers, handles or an incomplete binding select ambient authority? ABI decode rejects unknown numbers and release console 5 before effects. BSP `syscall_entry` (`bsp-qemu-virt/src/syscall.rs:166`) fetches table/window by current slot, generation-resolves the AS and fails closed if any component is absent. Actual scheduler accessors (`sched/mod.rs:530`, `:539`, `:547`) do not revalidate Task generation or table-pointer identity; the corrected overview/report expressly state that dependency on trusted registration and lifetime. The no-current/incomplete-context negative tests were read first.

8. **Validated mapping before user-pointer dereference — OK.** Malicious-caller question: can a console-cap holder use a kernel or non-USER pointer as a confused deputy? `copy_from_user` (`user_access.rs:182`) validates the window, probes each page, checks USER and copies through the translated frame's high-half pointer. Non-USER, unmapped and multi-page second-page-fault tests precede source inspection. The refreshed text asserts these concrete checks, not a general proof of hostile mappings or DEVICE exclusion.

9. **Range checking — OK.** Malicious-caller question: can wrapping length or one-past boundary arithmetic authorize unmapped bytes? Console validates the whole window before page probing/output. Loader computes the half-open span with saturating arithmetic and rejects `span_end > 1 << 48` before budget inspection; equality is legal and base zero is legal. Boundary, overflow and ordering tests (`task_loader.rs:1387`, `:1419`, `:1456`, `:1545`) support these claims. The seven-intermediate 8 MiB example agrees with the actual helper and its regression test (`:1498`); the chapter explicitly restricts this count to the current 4 KiB VMSAv8 format.

10. **Typed message parsing — OK.** Malicious-caller question: can arbitrary message bytes become unchecked privileged pointers or control values? `sys_send` constructs typed `Message`/cap-handle values from bounded register words before calling the IPC primitive; `sys_recv` returns encoded status/payload registers. The documented bare-primitive EL0 behavior matches `dispatch.rs:175` and `:200`; there is no claimed raw-byte parser or blocking syscall added. The raw-flat loader is separately identified as consuming a trusted embedded image, not validating arbitrary executable instructions.

11. **Cross-task authority conservation — OK for documented transfer.** Malicious-caller question: can sender-controlled IPC grant more authority than explicitly moved? Transfer validates the source `TRANSFER` right, moves an existing capability and preserves pending authority when receive capacity is exhausted. Notifications are separate objects with no v1 syscall. The EL1 bridge's unblock/yield behavior (`sched/mod.rs:1259`, `:1369`) is distinguished from EL0 bare calls, preventing readers from relying on non-existent scheduling/authority completion behavior.

## Verification and adversarial synthesis

The main attack considered is a misleading architectural claim becoming an unsafe implementation assumption later. In particular, the inspection challenged: hostile syscall 5 in release; absent/wrong/stale capability; non-USER or partially mapped buffer; incomplete binding versus stale Task generation; transfer with a full receiver table; overlapping loader source and allocatable PA; overflow/one-past span; cap/arena/PMM exhaustion; repeated load/exit leakage; FP/SIMD state assumptions; concurrent/preemptive reuse; and interpreting a successful serial demo as timer, idle, containment or memory-safety proof.

Actual code, not stale comments, settles those points. `dispatch` decodes before the console cap path despite old adjacent comments; the MMU writes per-task TTBR0 plus EPD0 clear/flush despite an old 'single global address space' comment; `syscall_entry` AS resolution does not imply Task generation validation; non-SVC panic affects the kernel; `task_exit_current` does not reclaim resources. The revised prose preserves each relevant distinction. FP/SIMD is enabled during boot and scrubbed at initial EL0 entry, but the trap frame does not establish full ongoing FP/SIMD isolation; this review supplies no such assurance. The one-core trusted hello evidence cannot prove it.
