## 1. Capability correctness

1. **OK — Privileged-operation authority.** Adversarial question: can an EL0 caller name another object without authority? IPC checks Endpoint SEND/RECV; console checks DebugConsole CONSOLE_WRITE; yield/exit bind to current self. Chapters explicitly classify root minting, arbitrary derive object correlation and kind-only memory helpers as trusted internal APIs, not exposed EL0 operations. No new operation is introduced.
2. **OK — Narrowest authority.** Question: can a broad or wrong-kind cap substitute for the needed right? Five live CapObject variants and eight named rights match source; Endpoint/console kind and operation rights are separate checks. No implemented MAP/WAIT/TaskControl or live MemoryRegion object is invented. Future operation/physical-memory ownership checks remain future work.
3. **OK — Checks precede effects.** Question: can failed authority mutate a message or emit bytes? IPC checks handle/kind/right/arena before transfer and console decodes/checks cap/range/probes before output. The prose correctly avoids a universal no-mutation error promise: endpoint generation housekeeping can reset stale state, and debug assertion versus release discard is explicit.
4. **OK — Move-only transfer.** Question: can sender and receiver both retain the transferred capability? `Capability` is neither Copy nor Clone; send validates TRANSFER and endpoint capacity before leaf-only cap_take, and receive checks free-list-head capacity before consuming/installing. Receiver gets a local root; retained peers/object aliases and loss of cross-table ancestry are explicit, so move-only is not misrepresented as unique authority.
5. **OK — Authorized duplication.** Question: can copy bypass DUPLICATE or add rights? cap_copy checks DUPLICATE/subset and preserves object identity, creating a peer/sibling or root peer. cap_derive checks DERIVE/subset/depth and creates a child; trusted caller-supplied new_object correlation is not runtime-enforced. Documentation accurately distinguishes these paths.
6. **OK — Revocation atomicity and scope.** Question: can revoked authority survive as a descendant or remote copy? cap_revoke performs a bounded, synchronous single-table descendant walk, preserving the source; no yield occurs within it. Peer roots and transferred remote roots are outside its ancestry. Chapters explicitly retain deferred ADR-0023 cross-table policy and do not promise global revocation, SMP atomicity or automatic object destruction.

## 2. Trust boundaries

7. **OK — Userspace input validation.** Question: can forged number/handle/current-task state reach an effect? Typed decoder/handle encoding and operation checks precede dispatch. BSP accepts table + window + generation-resolved AS as a unit; incomplete binding uses empty table/window and disables current-task effects. Trusted scheduler registration remains required: no separate Task-generation or table-pointer-identity validation is claimed.
8. **OK — Validated pointer use.** Question: can an arbitrary user VA be dereferenced as a kernel pointer? Console uses checked UserAccessWindow, translated USER leaves and physical direct-map copies, not raw user-pointer dereference. Stable valid mapping/backing ownership is a trusted prerequisite; generic copy APIs are not certified safe against arbitrary hostile mappings.
9. **OK — Buffer ranges.** Question: can overflow or a later unmapped page bypass validation? Checked range arithmetic, window containment and per-page USER checks precede console output; copy-to-user additionally requires WRITE. Empty ranges touch no bytes. Finite iteration does not imply an availability bound on an arbitrarily large permitted console request, and documentation makes no such guarantee.
10. **OK — Typed messages.** Question: can message data become privileged pointers or parser instructions? ABI decodes a typed Message of label plus three u64 words and separate optional cap handle. Payload words remain uninterpreted data; the kernel does not dereference them or claim to authenticate an application protocol/badge.
11. **OK — Cross-task authority.** Question: can receiver gain more rights than sender transferred? Both transfer stages preserve exact cap rights and reject missing transfer authority/full receiver capacity without consuming the pending cap. Receiver-local root insertion does not imply original-table revoke reaches it. Notification bit accumulation has no unimplemented wake/IRQ service or EL0 syscall attributed to it.

PhysFrame construction supplies alignment; free-time checks extent/reservation/allocation state. Trusted loader validates shape/range/budget/source overlap and maps RX image/RW-NX stack; partial rollback is not complete object destruction or arbitrary input safety.
