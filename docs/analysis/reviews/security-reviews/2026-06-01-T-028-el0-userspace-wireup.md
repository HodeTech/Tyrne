This is the **explicit EL0-boundary security review** the [T-024 §SEC-T024-01](../../tasks/phase-b/T-024-task-create-from-image.md) / [T-026 Definition of done](../../tasks/phase-b/T-026-current-task-cap-table.md) carry-forward demanded **before a real EL0 task runs** — the boundary is now attacker-observable.
- **Reviewer:** @cemililik (+ Claude Opus 4.8 (1M context) agent, acting adversarially across the eight axes of the [security-review master plan](master-plan.md), via a 5-lens / 9-agent adversarial workflow with per-finding skeptic verification — privilege-escalation, memory-disclosure/corruption, termination/context-switch soundness, capability/authority, lifecycle/isolation). Performed **2026-06-01** on the implemented + smoke-passing tree.
- **Scope:** the EL0↔EL1 syscall boundary now reachable by a real EL0 task: the wire-up ([`bsp-qemu-virt/src/main.rs`](../../../../bsp-qemu-virt/src/main.rs) — `load_image` → `task_create_from_image` → seed `USER_TASK_TABLE` → `add_user_task`), `syscall_entry`'s effect application ([`syscall.rs`](../../../../bsp-qemu-virt/src/syscall.rs) — `Resume` / `Reschedule`→`yield_now` / `Terminate`→`task_exit_current`), the new scheduler termination path ([`sched/mod.rs`](../../../../kernel/src/sched/mod.rs) — `task_exit_current` + the extracted `run_dispatched`), and the standing gates it activates: gate #1 ([T-025](../../tasks/phase-b/T-025-user-access-translation.md), UNSAFE-2026-0030), gate #2 ([T-023](../../tasks/phase-b/T-023-el0-entry-context.md), UNSAFE-2026-0032), gate #3 ([T-026](../../tasks/phase-b/T-026-current-task-cap-table.md), UNSAFE-2026-0014), the high-half regime ([T-022](../../tasks/phase-b/T-022-high-half-kernel-mapping.md) / ADR-0033).

## 1. Capability correctness

**Pass.** The EL0 task's `USER_TASK_TABLE` holds exactly one capability — a `DebugConsole` object with `CapRights::CONSOLE_WRITE`, at the root slot (index 0 / generation 0 = `tyrne_user::HELLO_CONSOLE_CAP`, asserted at the seed site). `syscall_entry` resolves capabilities **only** against the running task's own table (`Scheduler::current_user_table()` → `USER_TASK_TABLE`, gate #3) — never an ambient table, never `BOOTSTRAP_AS_TABLE` (which holds the kernel-side AS + Task caps) or the IPC-demo `TABLE_A`/`TABLE_B`. An EL0 task cannot name a capability it does not hold: a forged or wrong handle resolves in *its own* (single-entry) table and misses → `CapError::InvalidHandle`, never a cross-table grant ([ADR-0014](../../../decisions/0014-capability-representation.md) per-subject unforgeability holds). The `DebugConsole` cap is rights-checked (`CONSOLE_WRITE`) before any console emission. If the seed ever drifted off handle 0 the assert fails the build; at runtime a mismatch would fail closed (`InvalidHandle`), never over-grant.

## 2. Trust boundaries

**Pass.** The EL0→EL1 transition is the `SVC` trap to `VBAR_EL1+0x400` → the shared `tyrne_sync_trampoline` → `syscall_entry`; EL0 cannot choose where EL1 begins executing (the vector is kernel-fixed) nor smuggle a kernel code pointer (the trampoline saves the EL0 frame and routes by `ESR_EL1.EC`). The first EL0 entry (`enter_el0`, UNSAFE-2026-0032) **scrubs the entire EL0-visible register file** (`x0`–`x30`, SIMD `v0`–`v31`, `FPCR`/`FPSR`/`TPIDR_EL0`/`TPIDRRO_EL0`) before `ERET`, so no kernel state reaches EL0; `SPSR_EL1` = EL0t (`0x3C0`) so EL0 cannot return to EL1. On syscall return the trampoline restores the *saved* EL0 frame — EL0 cannot influence `ELR_EL1`/`SPSR_EL1` to land at a kernel address or EL1 (the saved `SPSR` is the EL0t one captured on the trap; the dispatcher writes only `x0`–`x7`). The control-plane effects (`Reschedule`/`Terminate`) hand off to the scheduler, which switches into a kernel-selected next-task context — not an attacker-influenced one.

## 3. Memory safety

**Pass.** The **confused-deputy** path (`console_write(cap, ptr, len)`) is closed by gate #1: every spanned page of `[ptr, ptr+len)` is resolved through the **task's own `TTBR0`** and **required to be `USER`** (`probe_user_pages` → `Mmu::translate`), behind the per-task `[entry_va, stack_top_va)` window first-gate — a non-`USER`, unmapped, block-mapped, or out-of-window VA returns `FaultAddress`, never a read. A high (kernel) VA cannot translate through the task's `TTBR0` (its low-half holds only the image + stack; the kernel is high-half in `TTBR1`), and the high-half is `UXN`/`PXN` from EL0 ([ADR-0033](../../../decisions/0033-kernel-high-half-migration.md)) — so EL0 can disclose neither kernel nor other-task memory through the console. `len` overflow is precluded (the window + per-page bounds). The new `task_exit_current`/`run_dispatched` abandon the exiting task's syscall frame and `context_switch` into the next task via a throwaway context — Miri (`--workspace --exclude BSP`, 259 kernel tests) reports **0 UB** over the refactor. W^X holds: the image maps `USER|EXECUTE` (no `WRITE` — EL0 cannot rewrite its code) and the stack `USER|WRITE` (no `EXECUTE`). The kernel `SP_EL1` (`USER_TASK_STACK`, 4 KiB) was not observed to overflow under the syscall handler call-tree (trap frame + dispatch + the gate-#1 walk + the console writer); see §8 for the empirical-bound forward-flag.

## 4. Kernel-mode discipline

**Pass.** The new scheduler termination path follows the established discipline: `task_exit_current` reuses `start_prelude` (the dispatch selection) + the extracted `run_dispatched` tail (shared with `start`), so the security-critical `context_switch`-abandon logic is **not duplicated**. It honours the [ADR-0021](../../../decisions/0021-raw-pointer-scheduler-ipc-bridge.md) "no `&mut Scheduler` across the switch" rule (the momentary borrow drops in `start_prelude` before the switch) and the `IrqGuard`/`DAIF` discipline (the switch runs under the masked SVC-handler exception state; the guard's `Drop` never runs on the abandoned frame, so the next task begins masked — identical to `start`). `syscall_entry` calls the scheduler from the SVC handler reading the write-once BSP statics (`SCHED`/`CPU`/`CONSOLE`/`activate_address_space`), single-core with IRQs masked — no aliasing. The `unsafe` surface is audited (UNSAFE-2026-0008 context-switch + UNSAFE-2026-0014 momentary `&mut` + UNSAFE-2026-0029 trap-frame, amended for T-028).

## 5. Cryptography

**Not applicable** — T-028 introduces no cryptographic operation.

## 6. Secrets and logging

**Pass.** The only emissions are the userspace greeting (a fixed `.rodata` string in the task's own image) and the kernel's `tyrne: userspace task exited` termination report — neither carries a secret. The register scrub (§2) is precisely the control that prevents kernel state from leaking into EL0 (and thence to any future EL0-visible channel). No syscall logs capability contents or buffer data.

## 7. Dependencies

**Pass.** No new external dependency. The EL0 program links only the in-tree `tyrne-user` crate; the image is produced by `rust-objcopy` from the already-pinned `llvm-tools-preview` toolchain component (ADR-0039) — the K3-8 `cargo-vet` flag stays unfired.

## 8. Threat-model impact

The boundary is now **attacker-observable**: a real EL0 task executes and issues syscalls. The adversarial review found **no privilege escalation, no memory disclosure or corruption, and no capability-model break** an EL0 task (or a buggy/malicious userland) can achieve in v1. An EL0 task can do exactly what its capabilities permit — `console_write` of its own `USER` buffer through the gate-#1 boundary, and `task_exit`/`task_yield` on its own identity — and nothing more.

Two findings were raised and **verified non-exploitable** (both refuted by independent skeptics against the live code):

- **(low) User-access window `saturating_sub`** — the per-task window is a pure *restriction* layered before the load-bearing per-page `USER` translate gate; a zero-length window only makes the task's own syscalls fail closed, never widening access, and the inputs are loader-fixed (not EL0-controllable). A defensive nit, already documented inline.
- **(medium) Orphaned exiting task's `task_states` slot remains `Ready`** — factually correct (`task_exit_current` drops the exiting task without clearing its state) but **inert in v1**: the exiting task's handle is unreachable (not in the ready queue — it was dequeued on dispatch and never re-enqueued; not idle; not `current`), the only by-state scan (`unblock_receiver_on`) matches `Blocked` exclusively, and its `TaskArena` slot is not freed so `create_task` cannot reuse it. It **reduces to the accepted SEC-T024-01 object-lifecycle gap** (see forward-flag).

### Verdict

**Approve.** No live security defect; **no fix required** to proceed. Five adversarial lenses with per-finding skeptic verification produced **0 confirmed exploitable defects**; four lenses clean, the fifth's one semantic finding verified inert in v1. The EL0 boundary is sound under the v1 threat model (single-core, cooperative, the documented lifecycle deferral). Gates: `cargo fmt`/`host-clippy`/`kernel-clippy`/`kernel-build` clean; **host tests 259 kernel / 46 hal / 58 test-hal / 3 doc**; `cargo miri test --workspace --exclude tyrne-bsp-qemu-virt` **0 UB**; QEMU smoke proves the full `+0x400` round-trip + clean `task_exit` to `tyrne: all tasks complete` with **zero new fault class**.

### Forward-flagged items (carry-forward; non-blocking)

- **SEC-T028-01 (object lifecycle on exit — extends [SEC-T024-01]).** `task_exit_current` drops the exiting task from scheduling but does **not** reclaim its `TaskArena` slot, address space, capability table, or kernel stack, and leaves its `task_states` slot `Ready` (orphaned). Inert in v1 (the handle is unreachable; the slot is not reused), but the successor object-lifecycle ADR should add a **terminal task state** (so a future by-state path cannot re-dispatch an exited task) and couple resource reclamation to AS/task destruction (so a reused slot/generation cannot alias an orphaned scheduler entry). Tracked here so the next lifecycle work closes it.
- **SP_EL1 stack worst-case not empirically measured.** `USER_TASK_STACK` is 4 KiB (matching the kernel demo stacks); the memory-safety lens found no overflow, but the worst-case syscall-handler call-tree depth (gate-#1 page-table walk + the console `FmtWriter`) was not measured. A `-d`-instrumented high-water check (or a guard page) is worth adding when EL0 syscalls grow richer.
- **IRQ-under-task-`TTBR0` relies on `TTBR1` implicitly.** While the EL0 task's AS is active, an IRQ handler reaches kernel memory only via the high-half `TTBR1` (the task's low-half lacks kernel mappings) — correct in v1 (documented in `run_dispatched`), but a forward-defensive invariant to assert when preemption/multi-AS lands (B5+).
